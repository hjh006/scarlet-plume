# OpenMetadata与Wazuh真实实例联调验收

2026年11月11日在本地Docker完成。本轮沿用赤翎既有工作区和数据卷，部署真实OpenMetadata与Wazuh实例，将实际来源结果接入同一检查、证据、整改复测、独立复核和报告流程。浏览器打标仍排除。所有业务数据为明确标注的本地合成样例；供应商原始材料、账户凭据、完整告警及样本原值未进入开源仓库。

## 真实目录、权限失败与恢复

1. 官方PostgreSQL ingestion先把实际样例结构写入OpenMetadata，再由赤翎采集器调用真实目录API。目录评估固定来源修订、运行、字段、采用标准、识别规则版本和覆盖限制；首轮6条自动G02证据已进入工作区报告。
2. 暂停该发现侧车，临时CLI仅替换OpenMetadata访问令牌，使用原平台任务令牌触发一次实际拒绝。运行69为 `collect/error`，报告中的来源 `current=false`；失败没有清空旧目录，也没有使G02通过。保存的正确令牌未被覆盖。
3. 恢复正确令牌后运行73重新成功。后续任务修订v2及自动运行77恢复 `current=true`，并观察到新建合成表与view；此前6条证据的JSON内容摘要逐项保持不变。维护数据库连接池配置并重启OpenMetadata期间，83/84再次正确记为连接失败；服务恢复后的85/89连续成功。最终23:51复查运行91成功、来源当前有效，未以早前单次成功代替持续采集检查。
4. 专用只读机器人实际读取表元数据返回200，读取连接配置和创建数据库服务均被403拒绝。此验证针对该OpenMetadata读取身份，不推导源数据库的完整权限情况。

本适配器此次收集的是元数据，内容覆盖仍为 `not_collected`，源数据库ACL仍为unknown。标签、字段名候选和注释不会变成内容检测或法定分类证明；当前14条历史与新增目录评估均保留缺条件，不能仅凭这些事实自动通过G02。原生数据库内容采集与目录元数据属于不同取证范围。最终复查时，带健康检查的服务均healthy，其他采集/桥接侧车running，未观察到OOM退出；配置与实际资源范围见各部署文档。

## 真实风险、故障与整改复测

| 步骤 | 来源与平台结果 |
| --- | --- |
| 发现 | 实际接口公开返回200，健康检查204，检查器确认固定合成JSON；Wazuh原生100501产生告警。平台事件6采用native ID `1794411626.3549`，自动进入检查37。 |
| 无复测时尝试通过 | 负责人提交后，独立复核人尝试通过被409拒绝，再退回整改。没有把来源正信号或提交操作当作通过。 |
| 故障 | 停止本轮合成接口，强制重新测量。真实Wazuh原生100503告警记录health/export均为0；该unknown不投影为消除信号。检查37保持 `needs_work`、`canSubmit=false`，平台没有clear。 |
| 整改 | 暂停检查器，恢复合成应用，将公开配置改为private；实际HTTP核对导出403、健康204后登记整改证据77，再恢复检查器并强制新测。 |
| 来源复测 | Wazuh原生100502产生native `1794411765.5599`，平台事件8。实际测量时间 `2026-11-11T15:42:43.167133Z` 晚于整改；同来源、资产、规则和API范围，自动登记 `operations-event:8` 复测证据。 |
| 独立复核 | 负责人再次提交，负责人自身必须回避；独立复核人核对证据后使检查37为verified。 |
| 重放与恢复 | 停止桥接worker，将已接受的真实native事件6重新投影到源端0600队列，重建worker后队列自动排空；该事件在平台仍仅1条，检查37仍为verified。无效队列文件保留为失败项，未静默丢弃；仅该测试文件随后显式清理。 |

故障阶段原生100503的实际记录包括 `1794411689.4241` 和 `1794411693.4920`。正常、故障、恢复都经过真实HTTP与真实Wazuh分析，未以预制平台事件代替。检查器与桥接器目前持续运行，样例配置保持private。

联调发现并修正了源端时间语义：平台的 `observedAt` 使用检查器实际测量时间，Wazuh分析时间仅作因果范围校验。延迟分析不能把整改前的旧测量变成“整改后复测”；延迟、未来和过期时间均有回归。最初版本的正信号为平台事件5，本次完整闭环及稳定重放采用修正后的事件6。

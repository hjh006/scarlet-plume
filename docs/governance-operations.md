# 治理办理

「治理办理」用于登记个人权利请求、同意与撤回、委托与供应商、审计与评估、事件报告和生成内容标识。每项记录关联本工作区的实际处理活动、检查、证据和适用依据，保存内容修订与独立复核历史。

办理完成表示人工独立复核已经留痕。源端删除、更正、停止处理、撤回传播、实际报送与收件仍须通过对应来源的真实证据核对。

## 角色与状态

| 操作 | 角色 |
| --- | --- |
| 查看台账、详情、冻结依据和历史 | 工作区成员 |
| 创建、编辑、开始办理、提交、取消；启动同意撤回 | 负责人或经办人 |
| 通过独立复核、退回补充 | 负责人或复核人，且不能是本记录的历史贡献者 |

创建后状态为 `draft`。一般流程为 `draft → in_progress → in_review → completed`。复核退回后为 `needs_work`，补充内容和证据后重新办理或提交。尚未进入复核的事项可以取消；没有删除记录的接口。

已完成的同意记录可启动撤回，进入 `withdrawal_pending`。逐系统补充实际传播证据后提交独立复核，通过后为 `withdrawn`。原同意的主体、目的、依据、告知版本、取得时间，以及撤回起点受保护，不能通过编辑回拨事实；原涉及系统不能移除。

## 办理步骤

1. 进入所需办理种类，查询现有事项；台账按编号从新到旧分页。新建前先确认没有重复事项。
2. 填写事项标题、责任人或团队、可选处理活动，以及适用性和事实理由。`unknown` 表示待核定，不能直接完成复核。选择“不适用”也须有理由、采用依据和关联证据。
3. 登记该种类所需的业务事实。主体引用只接受小写 SHA-256 摘要，不填写姓名、手机号、证件号或其他原始个人标识。时间填写真实时点和时区，计划与实际完成分别登记。
4. 按实际角色、服务范围和处理活动选择法规或标准版本。保存后冻结采用的依据；目录更新不会改写既有记录的已采用版本。依据标题或目录收录本身不证明适用或已满足要求。
5. 从本工作区的真实检查读取证据，再选择证据用途。也可填写已有检查和证据编号，服务端仍校验归属。若关联处理活动，检查和证据还须符合该活动的资产与活动范围。
6. 保存内容修订，再填写办理意见，开始办理或提交独立复核。由符合角色且独立于历史贡献者的另一个账号核对后通过或退回。

### 六类事项的证据要求

| 种类 | 完成前需要核对的事实与证据 |
| --- | --- |
| 个人权利请求 | 请求事项、接收时间、身份核验、办理结论、答复与送达证据。删除、更正、限制处理或撤回同意的满足、部分满足结论，需逐系统关联 `rights_execution` 证据；部分满足或拒绝须说明理由。身份核验失败仅能在有核验、答复和拒绝依据的情况下形成拒绝结论。 |
| 同意与撤回 | 处理目的、处理依据、告知版本、实际取得同意及 `consent_grant` 证据。撤回时逐系统关联 `withdrawal_propagation`，保留真实撤回起点。 |
| 委托与供应商 | 处理关系、目的与范围、合同引用、跨境判断和真实监督检查；`contract` 证据与有效合同期限分别核对。 |
| 审计与评估 | 审计范围、机构及关联方组、负责人、独立性说明、报告和实际完成时点。自然人数声明需有规模口径证据；内部计划不能代替完成报告。 |
| 事件报告 | 实际发现时间、分级、运营者类型、并行行业义务与实际渠道。需要报送的事项逐渠道关联初报、总结证据；引用存在不表示主管机关已收件。 |
| 生成内容标识 | 实际服务范围、模态、内容摘要、采用标准、提供者与内容引用，以及显式标识、隐式标识、导出保留观察和验证证据。未支持格式保持待核对；人工或元数据观察不等于密码学签名验签。 |

证据用途回执只能引用本记录已经关联的真实证据。详情中的证据问题列表会指出观察时点早于本次请求、撤回、报告或完成起点等问题；不能复用旧阶段证据完成新事项。提交和复核时由服务端再次检查。

## 期限与来源语义

期限卡片使用已采用依据和已登记事实计算，适用范围不明时保持 `pending_scope`。需要权威工作日历但未配置相应版本时保持 `pending_calendar`，不会把周一至周五当作完整法定工作日历。

权利答复、供应商复核与内部审计计划中的人工期限是业务登记，不被标成统一法定期限。时间已过和存在回执引用是不同状态；回执引用不自动证明源端执行、送达或收件。

## API

基址为 `/api/v1/workspaces/{slug}/governance-ops`，使用现有工作区会话与变更请求的同源校验。

| 方法与路径 | 用途 |
| --- | --- |
| `GET /catalog` | 种类、状态、法规与标准版本及范围说明 |
| `GET /records?kind=&status=&cursor=&limit=50` | 台账分页，返回 `items`、`nextCursor`、`hasMore` |
| `POST /records` | 创建草稿，返回完整记录 |
| `GET /records/{id}` | 内容、冻结证据与依据、期限、历史预览 |
| `PUT /records/{id}` | 完整内容替换，必须携带原 `revision` |
| `POST /records/{id}/actions` | `{revision, action, note}`；动作包括 `start`、`submit`、`approve`、`request_changes`、`cancel`、`withdraw` |
| `GET /records/{id}/history?cursor=&limit=50` | 较早历史分页 |

内容字段为 `kind`、`title`、`owner`、可选 `activityId`、`checkIds`、`evidenceIds`、`regulationIds`、`applicability`、`applicabilityReason`、按种类严格校验的 `details` 和 `receipts`。`receipts` 项为 `{purpose, evidenceId, system?}`，系统或渠道要求逐项精确关联。

更新时保留原修订，不能用刷新得到的新修订悄悄覆盖旧草稿。`400` 表示字段或引用无效，`403` 表示角色或独立性不满足，`409` 表示状态或修订已变化，`422` 表示完成条件或证据不足。失败后核对提示、最新状态与真实证据，再明确重试；历史读取不会执行源端业务动作。

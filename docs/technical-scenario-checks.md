# 场景技术检查、整改与报告证据

核对日期：2026-11-12。产品主线为“采集与分析 → 运行技术检查 → 符合、不符合及待核实项 → 整改建议或受控修复 → 新来源复测 → 独立复核 → 导出报告证据”。办理资料与分类上下文用于补充采用范围，不代替技术检查。

## 运行与证据契约

一次运行固定场景、任务、资产及活动修订、引擎版本、检查依据、技术规则版本和采用的来源证据。历史运行快照不因后续分类、来源、规则或处置状态变化而改写。复测创建新运行，并通过 `previousRunId` 关联原运行。

`ScenarioCheckRun` 的主要字段：

| 字段 | 用途 |
| --- | --- |
| `scenario`、`task`、`assetId`、`activityId` | 实际检查范围；任务可空表示场景综合检查，活动必须关联该资产并属于同一工作区 |
| `scope` | 可独立采用的运行时来源、服务、方法、路由、来源内主体、IP及起止时间；可选等值指纹Token |
| `assetRevision`、`activityRevision`、`engineVersion` | 采用版本 |
| `findings[]` | 逐项结果、依据、预期、观察、覆盖、缺条件和整改建议 |
| `evidence[]` | 来源、记录、观察时间、范围、摘要及受限快照 |
| `reportRequirements[]` | 报告材料要求与该次技术检查、证据的对应关系 |
| `snapshotDigest` | 原始运行快照摘要 |
| `previousRunId`、`retestState` | 原运行与本次复测的关系 |
| `actions[]` | 已关联受控处置的执行状态与回执；不改写原始发现 |

每项 `finding` 保留 `requirementCode`、`basis` 的标题、条款、版本和链接，以及 `ruleVersion`、`expected`、`observed`、`evidenceRefs`、`coverage`、`missingConditions`。监管要求与用于检查其中某一技术措施的具体规则分别列明。

`remediation` 包含 `advice`、`executable`、`kind`、`reason` 和可选的 `target`。`executable` 只表示该目标存在兼容的受控执行能力；真正执行仍经过现有来源、权限、版本、审批和有效期校验。

2026-11-12扩展后的引擎版本为 `existing-detectors-adapter-v2`，运行方式仍为 `stored_observations`。此前 `v1` 冻结运行保持原快照，不回填版本或新增检查项。结果值仍为 `compliant`、`non_compliant`、`needs_verification`，仅表示具体技术规则在采用范围内的结果。

资产范围继续提供 `classification_consistency`、`pg_public_select`、`protection_coverage`：分类一致性支持当前托管 PG，以及 MySQL、MariaDB、MongoDB 等目录采集的表和字段；直接授权技术基线使用匹配的托管 PG 观察。旧采集缺少配置修订、来源失效或覆盖不足时保留待核实，完整访问控制、静态加密及备份不由这些检查自动通过。

`v2` 另外适配真实运行时访问观察、既有版本化策略、接口登记/弃用基线及已批准的受限 API 验证结果。运行时范围可独立于资产或活动提交，不把数据库资产名称猜成对应接口。资产已有明确 `runtime-api` 或 `openapi` 来源与方法/路由时才可复用相应范围。未接入、过期、旧审计缺少捕获投影或预算外的范围继续待核实。

目录分类通过 `applyScenarioCatalogClassification` 复用既有不可变分类评估、同批次规则和源端有界格式统计。表使用已有评估采用条件；字段仅使用自身识别结果，父表快照只提供同次采集的来源范围，不借用其他字段的信号。来源身份、最新批次、配置修订、创建人权限、时效及完整发布规则版本均需匹配，人工确认后还需新的源端采集。正向属性与当前人工分类相容可记为该项符合，冲突可记为不符合；自定义标签、无正向内容统计、采样不完整及过期结果继续待核实。OpenMetadata 只采集元数据和标签，分类比较保留为待核实，不当作内容确认。

可执行修复包括受限 `revoke_select` 与 `block_api` 申请。PG仅针对唯一匹配执行器、当前配置和可撤销的 PUBLIC 表级直接授权。运行时仅对有真实G03发现绑定的当前 gateway、精确方法/路由提供临时整接口阻断；详见下文受控修复限制。无兼容执行器的发现仍给出建议与缺失原因。

## 运行时采用范围与判定门槛

`scope` 保存 `sourceId`、`service`、`method`、`route`、`subjectRef`、`clientIp`、`from`、`to`，以及可选 `valueFingerprint`。`subjectRef` 是来源内去标识引用，不能自动映射现实员工；指纹只支持客户授权域内等值关联，不接收待查原值。IP按来源报告的可观察地址处理，原生代理使用连接对端，不信任任意转发头或业务请求头。国家、接收方、目的地及业务量必须来自明确的授权来源配置/观察，不能通过公网IP猜国家、通过响应大小猜人数或通过接口方法猜导出活动。

运行时审计先在SQL中按工作区、来源、服务、方法、路由、主体、IP、时间及指纹筛选，再计算匹配分母和应用上限。场景与运营报告当前各采用最多200条匹配观察，超过预算显式标记截断；接口、主体或规则分析预算外追加待核实项。`observed` 保留请求数、命中数、可观察分母、窗口及采用阈值，业务量同时保留 `records` 或 `bytes` 单位。请求次数、记录条数与去重人数不混用。

真实阳性可以说明所选技术基线被触发。阴性判为符合还需当前有效来源、策略在该检查窗口开始前已生效、足够且未截断的同范围请求、该规则需要的完整捕获及已知维度。未观察告警、来源沉默、未知TLS、匿名成功但是否要求认证未知、缺少主体/IP/客户声明、采集不完整和过期窗口都不能成为符合。各来源的发现和复测独立保留；一个来源通过不会关闭同服务另一个来源的阳性检查，也不能推导整个服务消除了风险。原生代理的 `transport`/`transportHop` 只说明实际观察跳段，例如 `proxy_upstream`，不外推端到端TLS或数据库静态加密。

| 采用的现有规则或适配 | `v2` 实际检查范围 | 缺条件时的处理 |
| --- | --- | --- |
| 原运行时策略 | 敏感/凭据响应、已知认证要求、主体访问频次、错误率、配置时段，以及SQL注入/XSS/路径穿越模式信号 | 模式不冒充利用成功；未完整检查所需请求/响应或认证适用未知时不通过 |
| `over_collection` | 按来源、接口、方向和版本化允许类别比较实际字段信号 | 未配置允许范围、未检查该方向或缺业务合法依据时分别保留技术/法律缺口；不自动宣称违反隐私政策 |
| `credential_cleartext_transport` | 非空凭据字段信号与明确HTTP跳段联用；HTTPS完整观察可支持该跳段的阴性 | 字段名不能证明存储明文；未知传输或未观察凭据不能替代该用例的证据 |
| `subject_multi_ip`、`subject_multi_region`、`client_region_mismatch` | 同来源主体不同IP/国家声明计数，声明地区与组织允许范围比较 | 多IP不证明多人共用，地区变化不证明账号被盗；缺标签保持未知 |
| `subject_repeated_access`、`volume_limit` | 配置窗口内重复请求，以及明确单位的累计业务量阈值 | 重复访问支持最长1440分钟窗口，其他策略仍最长60分钟；不推导人数、恶意意图或法定阈值 |
| `recipient_scope`、`destination_scope` | 明确接收方、目的国/域名与组织登记基线比较 | 单端声明不证明双端实际流转或物理跨境，缺少约定范围不能推导备案义务 |
| 接口生命周期 | 当前完整契约与已观察成功响应对比：未登记或已弃用接口仍成功服务 | 没有有效完整契约或只有失败/无请求时不推断下线完成，不外推未观察接口清单 |
| 受限API验证 | 当前批准计划/修订、来源及审批人仍有效、完整对照且新鲜的用例结果 | 连接测试和不完整对照为未知；指定某个运行时来源时不能借另一执行器的同名服务结果证明该来源 |

现有运行时策略共18种，新增9种策略默认关闭，负责人明确配置范围与阈值后才启用。它们比较的是组织采用的技术基线，不自动生成监管阈值。范围基线、完整规则命中与既有业务事实分别保留。

## 接口与操作顺序

下表路径均位于 `/api/v1/workspaces/{slug}`。

| 接口 | 作用 |
| --- | --- |
| `POST /scenario-check-runs` | 提交 `scenario`、可空 `task` 及资产/活动或独立 `scope`，运行检查并固定证据；带 `previousRunId` 创建复测 |
| `GET /scenario-check-runs` | 按 `scenario`/`task`、`assetId`/`activityId` 及平铺运行时范围查询，SQL筛选后取最近50条 |
| `GET /scenario-check-runs/{run}` | 读取运行快照及关联处置状态 |
| `POST /scenario-check-runs/{run}/findings/{finding}/remediation` | 提交 `reason`、`durationMinutes`，为可执行发现创建受控处置申请 |
| `POST /operations/controls/{control}/approve` | 独立人员按现有权限及修订号批准申请 |
| `POST /operations/controls/{control}/rollback` | 按现有权限、修订号及原因请求回滚 |
| `GET /scenario-check-runs/{run}/export?format=html\|json\|csv\|zip` | 导出该次检查、发现、报告要求与证据包 |

运行时历史查询使用平铺参数 `sourceId`、`service`、`method`、`route`、`subjectRef`、`clientIp`、`from`、`to`；时间采用含时区RFC3339。维度按采用值匹配，时间按冻结窗口重叠筛选。复测须保持原场景、任务和对象/运行时维度，不能把换来源、换主体或换IP称作同范围复测。`same_source_observation` 表示只重算原观察，`new_source_observation` 才表示采用了新的来源记录及观察时点。

运行检查会采用已接入来源的数据。需要新的源端观察时，先运行相应采集或获批验证，再创建复测；读取已有快照不等于刚刚对源系统进行了新探测。

受控修复的顺序为：申请 → 独立批准 → 来源执行 → 执行回执 → 新鲜来源复测 → 检查独立复核。`applied` 表示执行来源回执成功；它不等于技术复测通过或监管检查通过。

## 受控修复限制

场景修复接口只接受原因与持续分钟数，不接受客户端自选SQL、数据库角色、来源或接口目标。服务端从冻结发现读取受限目标，并再次检查当前来源授权、规则版本、近期真实阳性、G03检查绑定和精确目标。来源创建人被降权、策略改变、目标改变或缺少新证据时拒绝新申请。同一运行/发现重复申请关联同一处置，不重建冻结运行。

场景中的 `block_api` 入口限于 `missing_auth`、`over_collection`、`credential_cleartext_transport`，以及未登记/弃用接口的阳性发现；其他策略命中不因此获得自动执行能力。

`block_api` 会影响该接口的全部访问者。因此，按主体、IP或具体值指纹选取的子范围，以及策略本身只针对某主体/IP时，不提供扩大为整接口的自动入口。其他可执行项也须有唯一当前 gateway、同来源精确方法/路由和真实未关闭G03发现。批准API验证目标与gateway上游之间缺少显式可信绑定时，仅有同名服务或路由不够，保留建议，不借任意网关执行修复。PG申请继续核对配置修订、host/port/database/schema/table和PUBLIC目标，不对任意角色或任意SQL扩展执行。

2026-11-12后续更新：新增9项策略已接通 `persistRuntimeDetectionRetests` 自动复测。草稿登记真实整改或成功apply回执后即可等待来源复测，无需先手动提交、再由人工退回整改；只有原阳性观察不能手动送审。满足当前策略完整新窗口后，系统记录复测证据及新的submitted事件，自动进入 `in_review`；原作者、提交人或证据贡献人不能独立通过，仍须负责人/复核人按原贡献人回避及修订号门槛手动审核。原有9类规则保留既有工作流。

自动复测限定同source、方法、路由、ScopeKey及原受影响主体/上下文。完整窗口及起点观察须晚于最新整改、阳性和策略生效，实际样本与分母明确，来源沉默、未知捕获、截断或仅换主体/IP不通过。超范围类别须目标方向完整捕获且无剩余禁止类别；HTTP凭据须原方向/原跳段有实际凭据的完整HTTPS观察，凭据消失或单个403不能替代TLS证明。主体多IP、多地区及重复访问逐个覆盖所有原触发主体；国家/接收方/目的地须零基线偏离，业务量须同一量纲且累计不超上限。路径掩码 `json_dynamic_keys` 保留为说明，不能仅因路径精度降低否定仍完整的类别统计；size/depth/fieldLimit/invalid等真实不完整继续阻断。

合并发现累计保存触发主体、已知subject/IP及凭据跳段/方向，不因最后一个主体安静清除其他主体。迟到的新受影响上下文即使观察时间相同或更早，也会合并并使尚在复核的旧证明失效；同范围无变化重放不重复送审。旧记录没有这些上下文时，只在完整保留样本足以重建原窗口时采用，不猜测遗失范围。

`CheckDetail.runtimeRetest` 返回 `awaiting_remediation`、`awaiting_observations`、`passed`、`invalidated` 或 `verified`，同时给出原因及可选 `nextEligibleAt`；该时点只是最早窗口条件，不承诺届时来源必有足够数据。新阳性使原复测失效并回到整改；策略暂停、来源撤销、创建人授权失效或长期无有效观察均不能继续独立通过。自动复测观察超过24小时后需新完整窗口刷新，生成新复核修订，旧reviewRevision不能通过。

同一ScopeKey/Source/Method/Route/Subject/IP/方向及业务量单位边界不变时，策略修订或重新启用仍有恢复路径：登记晚于当前修订的真实新整改，再取得当前版本完整窗口。证明同时冻结原命中与本次采用策略，证据摘要列明两者版本供独立人员核对；仅改策略或复用旧整改不能通过。缩小原适用边界、改变方向/量纲或原上下文无法还原时仍待核实。

检测样本保留25小时、每来源最多20000条，为最长1440分钟重复访问窗口保留起点观察缓冲；达到预算不自动复测通过。访问审计明细的7天限制不变。场景快照、原检查自动复测、执行回执和独立通过分别记录；不是每种规则都有受控执行器，阻断成功也不能冒充各规则的阴性证据。

## 现有检测和修复能力

| 可复用实现 | 可以确认的技术事实 | 结果边界与整改 |
| --- | --- | --- |
| `classificationstandards.EvaluatePostgreSQL`、`compareAutomaticClassification`、目录不可变分类评估 | 字段名、注释、类型线索；受限样本内格式命中；与已登记分类的相容或冲突情况 | 格式命中不证明真实身份、用途、去重人数或法定类别；行业标准正文未实现的条款保留待核实。分类修订通过现有确认工作流完成 |
| `evaluatePostgresInspection`、`postgresPermissionIncreased` | PostgreSQL 表和字段直接 SELECT ACL、PUBLIC 授权、schema USAGE、与已复核快照相比新增的直接授权 | 原函数的 `review_required`、`no_signal` 不是整项访问控制的合规结论。若技术规则检查“无 PUBLIC 直接 SELECT”，结论只覆盖该狭义规则；是否违反批准范围仍须核对。继承权限、有效访问、RLS 影响、加密和备份不能由直接 ACL 代替 |
| `evaluateRuntimeFindings`、`evaluateRuntimeDetection` | 与当前接口契约不一致的成功响应；选定来源、路由、窗口和策略版本内的敏感响应、认证状态及其他信号 | 未观察到告警不表示安全；采集不完整、未检查请求或响应、窗口不足、策略变化保留缺口。SQL 注入、XSS、路径穿越模式仅为观察信号，不直接证明可利用漏洞 |
| `apivalidator.Execute`、`validationRuleOutcome` | 获批只读用例下的对象越权对照；已提供单个凭据与本地弱凭据规则的受限验证 | `vulnerable` 要有完整正向证明；`not_observed` 仅为本用例未发现；`connection` 模式及缺失身份、对象或对照证明为 `inconclusive`。不枚举对象、不爆破凭据、不推断全系统无漏洞 |
| `CreateControlAction(kind=block_api)` 与 runtime-agent | 在已观察的 gateway 来源和已配置路由模板上执行临时路由阻断 | 仅支持已授权网关路径；不表示所有路径均被阻断，也不修复业务代码 |
| `CreateControlAction(kind=revoke_select)` 与 control-agent | 对匹配托管 PostgreSQL 来源的表级、直接、非可转授权 SELECT 撤销，以及受约束恢复 | 仅支持已采集的角色或 PUBLIC、配置 schema 和表；不执行任意 SQL，不撤销字段级授权或展开继承权限。源端变化、可转授权、目标不匹配或权限不足时失败并保留原因 |

API 受限验证的 BOLA 结论需要：所有者账户访问自身对象被确认、另一账户访问其自身对象被确认，再对同一目标完成交叉访问。只有完整对照且无缺口时才产生确定的用例结论。弱凭据验证只检查预先获准、已提供的凭据。

现有运行时阈值是工作区策略配置，不是自动生成的监管阈值。未实现或未取得证据的要求继续为待核实，不自动补成符合或不适用。

## 复测复用的现有门槛

- 多源分类：`catalogClassificationCheckAllowed` 与场景只读适配器核对来源启用、配置修订、最新成功采集、时效、采用规则、分类修订和不可变事实摘要；人工确认后须有新的源端观察。目录证据以 `discovery` 来源固定批次、观察时点及范围，复测不将同一旧批次重算当成新来源采集。
- PostgreSQL 撤权：`controlVerificationAllowed` 要求成功 apply 回执、配置目标仍匹配、晚于执行的最新成功采集，以及该角色或 PUBLIC 的目标表级直接 SELECT 已不存在。
- 运行时：`runtimeRetestAllowed`、`runtimeDetectionRetestAllowed` 核对来源、路由、策略版本、整改和最新正向发现之后的观察。敏感响应需要明确检查过响应，认证检查需要明确认证状态或拒绝结果，模式信号需要新的完整请求检查；来源沉默不能复测通过。
- 独立复核：`SubmitCheck`、`ReviewCheck` 继续使用既有证据时序、来源绑定、贡献人回避与修订约束。运行结果、执行回执、复测和人工复核分别保留。

## 要求、技术控制、证据与报告的对应关系

| 已登记要求或场景 | 可自动提供的证据 | 仍需业务确认或另行取得 | 可复用输出 |
| --- | --- | --- | --- |
| G02 分类盘点 | 结构、规则版本、受限格式统计、分类修订及冲突、覆盖限制 | 行业适用、实际用途、重要或核心数据依据、完整数量与影响 | 技术运行证据、目录分类评估、检查历史、合规报告 |
| G03 访问控制与其他保护措施 | 直接 ACL、接口契约/运行时差异、受限主动验证、处置回执、新来源复测 | 批准访问范围、继承和实际访问、未接入路径、加密备份及其他未验证措施 | 技术运行证据、API 验证报告、处置与复核时间线 |
| personal / P04 个人信息影响评估 | 上述技术事实、已确认分类、已登记活动及风险和措施验证记录 | 处理依据与必要性、个人权益影响、事前评估时点、实际主体和完整范围 | 完整专项评估导出，并附技术检查与整改证据 |
| domestic 重要数据风险评估或迎检 | 已确认资产及分类、技术控制、风险事件与整改、复测和独立复核记录 | 处理者身份、重要数据依据、完整处理概况、组织责任、行业格式、正式报告签章与报送 | 技术证据包和检查报告可作为底稿；正式风险评估报告按实际适用要求编制 |
| crossborder / T03 | 活动登记中的接收方、地域、路径、分类及可观察流向；本次技术措施和验证证据 | 实际出境、关基身份、完整去重口径、例外、合法性、接收方保障、法律文件和正式申报 | 内部数据出境评估、PIA 及技术证据；申报材料依当前官方指南另行核对 |

个人信息合规审计、个人信息影响评估、重要数据风险评估和数据出境安全评估分别采用各自的要求及办理范围。检查通过记录不能改名代替另一类正式报告。

## 报告要求字段

`reportRequirements[]` 采用 `ScenarioCheckReportRequirement`：

| 字段 | 含义 |
| --- | --- |
| `key`、`title`、`basis` | 报告要求标识、名称，以及采用条款、版本和官方链接 |
| `applicability` | 具体适用前提；缺少身份、通知、实际活动等事实时明确保留待确认 |
| `requiredDeliverables` | 对应场景需形成的报告内容或记录，不把技术规则命中替代完整报告 |
| `findingIds`、`evidenceRefs` | 本次运行中可支持该报告要求的技术发现和固定证据引用 |
| `coverage`、`status`、`missingConditions` | 实际支持范围、材料准备状态、未覆盖的条件；材料准备状态不表示监管受理或批准 |
| `externalSteps` | 需另行完成的专业判断、报告签章、提交、回执等步骤 |
| `retentionNote` | 适用的保存要求及当前平台保留能力边界 |

报告引用应能从要求追溯到技术规则、源端运行、固定证据、整改动作和复测。正式提交或接收凭证应来自真实记录，不由技术运行生成。

当前内部技术检查证据包的材料状态为 `available`；条件性监管报告根据已取得来源证据列为 `partial` 或 `missing`。适用性字段分别为 `applicable`、`conditional`，不会由技术计数生成监管报告已通过的状态。

## 已核对的报告依据

以下依据用于材料映射，不自动判断当前用户已满足适用条件；不添加未经核实的行业阈值或专门格式。

- [个人信息保护法第55、56条](https://www.cac.gov.cn/2021-08/20/c_1631050028355286.htm)：适用时须事前评估并记录处理情况；评估涵盖合法、正当与必要性、权益风险及保护措施有效性，报告和处理记录至少保存三年。现有 PIA 模板保留这些业务和证据题，分类上下文只是可选辅助。
- [网络数据安全管理条例第33条](https://www.cac.gov.cn/2024-09/30/c_1729384452307680.htm)：重要数据年度报告需要处理者及责任信息、数据处理概况、制度与技术措施有效性、风险事件处置、提供/委托/共同处理评估、出境情况及主管部门补充内容。数据概况不包括数据内容本身。技术检查只能支持其中已取得的技术事实。
- [网络数据安全风险评估办法第15、16、18条（商务部政府网站转载）](https://policy.mofcom.gov.cn/claw/clawContent.shtml?id=106660)及[国家网信办实施问答](https://www.cac.gov.cn/2026-08/20/c_1788889498173657.htm)：重要数据年度风险评估报告至少保存三年，评估完成后20个工作日内按主管部门要求报送；特定部门要求的委托评估另涉及报告签章及整改完成后15个工作日内报送整改情况报告。需要记录真实评估完成、整改完成及主管要求，不能把采集时间当作这些起算事实。
- [个人信息保护合规审计管理办法第10、11条](https://www.cac.gov.cn/2025-02/14/c_1741233507681519.htm)：按保护部门要求开展的审计涉及专业机构报告签章、报送，整改完成后15个工作日内报送整改情况报告。平台技术检查可提供相关底稿，不能生成专业机构签章或接收凭证。
- [数据出境安全评估申报指南第三版公告](https://www.cac.gov.cn/2025-06/27/c_1752652339765002.htm)及[2026年7月官方问答](https://www.cac.gov.cn/2026-07/24/c_1786638883119336.htm)：申报和延长办理需依据当前适用情形、指南及官方系统。这里提供技术证据映射，未导入或声称覆盖指南全部官方表单。

## 运营调查与日、周、月报告

运营调查采用同一运行时范围生成独立不可变快照，包含匹配观察分母、采用节选、来源有效性、逐项技术分析与策略版本、当前保留的风险周期、执行引用、覆盖和缺条件。已授权成员可读，负责人/操作人可生成报告；周期任务配置仅负责人可改，带修订号。报告不是正式监管结论，也不自动完成签章或提交。

| 工作区接口 | 作用 |
| --- | --- |
| `GET /runtime-evidence` | 同范围审计查询；先筛选再计数/截取，保留来源及捕获限制 |
| `POST /operations-reports`、`GET /operations-reports` | 用 `title`、`scope` 冻结报告；按明确维度/窗口筛选后列最近50条 |
| `GET /operations-reports/{report}`、`/{report}/export?format=html\|json\|csv` | 查看或导出冻结分析、结构化证据、分母、缺口及摘要 |
| `GET/POST /operations-report-schedules`、`PUT /operations-report-schedules/{schedule}` | 查询及配置 `daily`、`weekly`、`monthly` 日历任务、时区、静态范围、启用状态及修订 |
| `POST /operations-report-schedules/{schedule}/run` | 立即生成最近一个已完成的自然周期，返回报告本体；同任务/周期重复运行返回同一报告 |

当前服务定时worker领取到期任务，只在平台内冻结可下载报告，不自动邮件投递。默认 `Asia/Shanghai` 时区，周从周一开始，月按真实日历边界计算，包含闰年二月的实际天数；不把固定30天称为月报。配置中的临时 `from`/`to` 不用于周期任务，由每个完成周期计算。任务创建人不再具备负责人权限时，不继续自动生成。

访问明细目前保留7天并受每来源条数上限约束。周报/月报超出实际保留或采用预算时明确列缺口，缺失天数不补零；历史周期快照也不反向补造完整源日志。真实身份、岗位/离职事实、业务授权、完整流量与法律适用仍须补证。CSV对公式前缀转义，HTML转义动态字段；结构化快照和摘要用于核对采用内容，不是监管签收。

## 导出与保存

场景技术运行支持 HTML 报告、JSON 快照、发现 CSV 和 ZIP 证据包。ZIP 包含 `report.html`、`run-snapshot.json`、`findings.csv`、`linked-actions.json`、`evidence/001.json` 等逐项证据及 `manifest.json` 的 SHA-256 清单。`linked-actions.json` 明确记录导出时点的处置进展，与冻结的运行判定分开。证据是结构化引用和受限采集快照，不追加源表原始行、原始业务日志或请求/响应正文。摘要用于校验包内文件，不是外部签名或监管接收凭证。

已有输出继续可用：

| 输出 | 接口及保存范围 |
| --- | --- |
| 当前检查合规报告 | `GET /reports/compliance` 及 `/export?activityId={id}&format=html\|json`；同一数据库快照读取检查、证据、时间线、目录和处置；专项评估部分仅保存引用 |
| 托管 PG 自动归档 | `GET /reports/archives`、`/{archive}` 及 `/{archive}/export?format=html\|json`；固定该次来源和检查，当前每个任务保留最近30份 |
| 完整专项评估 | `GET /assessments/{id}/export?format=html\|json`；包含采用模板、活动、事实、答复、缺口、证据与审核记录；送审和通过报告采用对应冻结版本 |
| 受限 API 验证报告 | `GET /api-validation/plans/{plan}/export?format=html\|json`；包含采用计划与修订、受限请求计数、源端对照证明和缺口 |

当前合规报告超过200项检查或3000条证据与时间线会要求缩小范围；PG 自动归档还有大小上限。最近30份轮转与导出功能本身不实现法定三年保管。需要长期保存的正式材料应安排符合实际要求的归档和访问控制，并保留采用版本与真实提交记录。
